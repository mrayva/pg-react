## 1. User-visible outcome

A review case that becomes overdue while the business tables are idle is evaluated by the managed runtime and receives at most one permitted escalation for each configured level in its MDM case occurrence. Restart, retry, audit updates and human edits do not create uncontrolled escalation loops.

The existing due date remains authoritative unless a reviewed policy replacement explicitly authorizes changing it. React requests `ESCALATE` through the same typed transactional MDM adapter as other controls; MDM retains authority to accept or reject it. [S0 §§4–7]

## 2. Entry gates and scope

The 0.48.0 transaction, deduplication, binding and stale-work gates must pass on the exact stack. MDM must define escalation eligibility, maximum levels, manual protection, recurrence, duplicate/no-op behavior and action-driving revision semantics. The managed React deadline/temporal entry point must be mapped from the installed public contract rather than guessed.

Require the real MDM M2 `ESCALATE` implementation and its exact receipt fixtures. MDM `0.11.0` does not implement escalation. pg-trickle `0.108.0` does not make a `now()` predicate a time-only trigger; its EXTERNAL graph mode also excludes IMMEDIATE maintenance. Keep the existing React temporal path and prove idle-case liveness on the selected joint profile. [S8, S9]

The release adds managed time-only reevaluation and the signed bounded escalation profile. It does not add rolling/hopping event windows, business calendars, a new scheduler, arbitrary sequences of events, network alerts or human approval routing. The ordinary pg-react poll/worker model remains the runtime. [S0 §4; S7]

## 3. Implementation design

### 3.1 Audit and reuse the installed temporal path

Start by identifying the exact public temporal/deadline registration and execution path in the selected runtime, its ownership, granularity and recovery contract. The baseline concepts establish that advanced temporal/deadline facilities exist, not that any guessed function signature is supported.

Write an executable proof that a deadline initially in the future is evaluated after time passes without modifying the business source tables. If the supported path needs an explicit sampled-time relation, use its approved managed maintenance mechanism and document that technical input. Do not introduce arbitrary wall-clock polling or a separate scheduler as a fallback.

Only proceed beyond the audit task when the selected path can satisfy liveness. A missing temporal mechanism is a discovered core dependency requiring re-estimation, not permission to hide a `now()` expression in a materialized condition.

### 3.2 Explicit time semantics

Capture one authoritative database-time sample per evaluation unit through the supported mechanism. Apply a documented boundary rule for `due_at == sampled_time`; the proposed first profile treats equality as due. Use timezone-aware timestamps and the already qualified UTC elapsed-time service-window profile.

Persist or expose enough public evaluation-time evidence to explain why the case was eligible. Time is a policy input, but it must not become a request-key salt. A later sample with unchanged eligibility must not manufacture a new intended action or reset a deadline.

Freeze the allowed detection/dispatch latency budget from the configured managed poll interval and measured queue behavior before acceptance. Record both “became due” and “control accepted” times; a worker wakeup alone is not proof of delivered escalation.

### 3.3 Bounded escalation policy

Use the MDM-owned open/closed state, due date, current or previously applied escalation state, automation protection, active policy binding and configured level limits. Only emit a desired control that differs from current MDM state and is permitted by MDM.

**Proposed first profile:** progress to at most one next permitted level per case per evaluation, then reevaluate after committed MDM state is visible. Bound total levels and per-cycle admissions. Emit at most one condition row per MDM `case_key`; the next level is an action-driving payload value, not a new composite ordinary semantic key. Do not replay every missed time interval as a burst of escalation work after downtime. The policy owner must agree to catch-up semantics before tests are frozen.

“Same request is deduplicated” alone is not enough: a new lifecycle generation or action revision can produce a new request key for the same level. Jointly prove the semantic invariant across such keys. MDM must expose/validate the necessary occurrence and applied-level state, or the approved adapter must retain minimal delivery-deduplication state atomically with the intent. This is action bookkeeping, not a human review ledger. The chosen mechanism must be in the signed contract and survive restore.

A human's change must not allow a previously applied level to be silently reissued for the same occurrence. Genuine recurrence is identified by MDM, not inferred from a disappearing/reappearing row or a publication timestamp.

### 3.4 Prevent feedback and preserve deadlines

Define explicit watched/action-driving columns. Exclude receipt timestamps, worker heartbeats and audit-only publication updates from work creation. Preserve these fields as observation metadata when useful, but do not let them advance the action-driving revision.

After stale tokens, use the existing bounded reevaluation path. A new time sample does not make a stale payload valid. Existing attempted work remains immutable; a changed intended action requires a new item.

An accepted queue assignment or escalation can change the published MDM projection. Ensure that this feedback leads to a no-op once the desired state is reached. Due-date setting must not keep extending its own deadline on every publication. Authorized deadline replacement must be explicit, reviewed and tested against already queued escalation.

### 3.5 Public operational evidence

Expose through public React/adapter views or existing explanation output: original due date, configuration version, sampled evaluation time, requested/applied level, no-op/protection reason, pending work, receipt and stale/rejected outcome. Keep delivery, case closure and business resolution distinct.

Proposed files: `integrations/pg-mdm/sql/deadline-runtime.sql`, `escalation.sql`, action-column mapping and `tests/integrations/pg-mdm/time/`. No new generic temporal DSL or scheduler is introduced.

## 5. Acceptance tests

| ID | Scenario | Expected result |
|---|---|---|
| T49.01 | Open idle case crosses due time | Evaluation and permitted control occur within the predeclared bound without business-table changes |
| T49.02 | Immediately before/at/after due time | Boundary behavior matches the documented rule using a consistent time sample |
| T49.03 | Repeated polls at same eligible level | At most one applied escalation for the same MDM case occurrence and configured level |
| T49.04 | Retry/crash around escalation commit | Existing immutable key/body is reused; atomic control/receipt/completion behavior retained |
| T49.05 | New generation/revision but same occurrence/level | No duplicate semantic escalation even when a new work identity could otherwise be generated |
| T49.06 | Worker down across several deadlines | Bounded documented catch-up; no unbounded burst, lost eligibility or repeated applied levels |
| T49.07 | Audit/receipt/heartbeat/publication-only changes | No new command solely because observation metadata advanced |
| T49.08 | Existing due date and policy replacement | Deadline preserved by default; only explicit authorized replacement changes it; queued incompatible work is blocked/withdrawn |
| T49.09 | Human closes case or protects assignment | Stale pending escalation cannot override current MDM state |
| T49.10 | Genuine recurring review | New MDM occurrence can receive its permitted actions without reusing a prior occurrence's request identity |
| T49.11 | Maximum level and suspended binding | Level bounds enforced; paused/disabled bindings accept no new intents after the barrier |
| T49.12 | Mixed due workload under resource limits | Per-cycle bounded admissions, measured backlog behavior and eventual progress within the declared supported profile |

Use deterministic time-input fixtures for boundary enumeration and at least one real managed-runtime wall-clock test for liveness. Test synchronization should observe public state with a bounded deadline, not rely on a fixed sleep as evidence. Required real-time cases cannot be replaced by manually updating the business rows to force refresh.

Apply common gates C01–C12 to the now-present behavior. Correctness budgets for repeated controls and unauthorized actions remain zero.

## 7. Upgrade and recovery

Append the adjacent migration for temporal registrations/configuration and any minimal delivery-level bookkeeping. Keep existing request codec versions and previously applied MDM levels intact. Enabling a new escalation policy must be explicit and reviewed; an upgrade cannot silently turn on escalation for existing cases.

Pause adapter admission, reach the barrier and preserve coherent state before changing temporal configuration. After restart/restore, recheck artifact/capability identity, active binding and current MDM facts, then resume bounded evaluation. Do not reset original deadlines to recovery time or treat every missed poll as a new action.

Use the common clone startup guard. No cloned database may run overdue automation merely because copied timestamps are already in the past. A persisted “enabled” flag is not sufficient isolation.

## 8. Definition of done and scope cut

R3 completes when time-only liveness, deadline preservation, semantic per-occurrence/level uniqueness and feedback convergence pass on the real stack. The qualified temporal API and numeric workload-specific latency/admission bounds are documented.

Cut extra escalation profiles, advanced calendar rules and convenience metrics first. Do not cut real time-only testing, recurrence identity, duplicate prevention across new keys, or restart catch-up safety. If the temporal audit finds missing generic functionality, split that work into a new approved release rather than exceeding six person-weeks silently.
