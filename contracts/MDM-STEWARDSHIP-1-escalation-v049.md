# MDM-STEWARDSHIP/1: v0.49 bounded-escalation addendum

Status: **implementation decision for review**, 2026-10-19. This is an additive v0.49 profile over approved MDM-STEWARDSHIP/1 revision 3, **not** a retrospective change to that approved contract or a signed v0.49 release acceptance. Joint owner/reviewer sign-off and operating bounds remain required by pg-react #11/#12.

References: [React implementation](https://github.com/trickle-labs/pg-react/issues/11), [React qualification](https://github.com/trickle-labs/pg-react/issues/12), [MDM M4](https://github.com/trickle-labs/pg-mdm/issues/5).

## Decisions

1. **Authority and occurrence.** MDM remains authoritative for case identity, eligibility, due time, controls and receipts. `case_key` identifies one MDM review occurrence; recurrence creates a different key. React never modifies MDM tables directly and continues to call the existing `mdm_steward.submit_policy_intent` signature in the existing atomic work transaction.
2. **One automated application per level per occurrence.** The durable semantic identity is `(case_key, level)`, independent of request key, binding ID, policy revision, React generation, and action revision. MDM derives previously automated applied levels from its retained `policy_receipts_v1` rows with `action = 'ESCALATE'`, `outcome = 'APPLIED_CONTROL'` and the numeric `control.escalation_level`. No separate ledger or public API is introduced for this narrow change. The MDM case-row lock serializes the history check with the control/receipt transaction.
3. **Manual changes.** An authorized human may lower the current level. This does **not** erase any previously *automatically applied* level. A future automated request cannot apply that level again, even under a different request key or binding. Purely human-set levels do not themselves count as automated applications. The human may restore the level or a genuinely new occurrence may progress independently. `manual_assignment_protected` protects queue assignment, not escalation; pause/replacement and freshness gates still protect escalation.
4. **Outcomes and retries.** An identical authenticated `(binding_id, request_key)` retry replays its original receipt without a new effect, including after a human level change. A *new* request for an already automated-applied level returns a durable terminal `ACTION_DENIED` / `ESCALATION_LEVEL_ALREADY_APPLIED` receipt, with unchanged case controls and action revision. The existing `STALE_CASE` / `ESCALATION_NOT_NEXT`, `LIMIT_EXCEEDED` / `ESCALATION_LIMIT`, `ACTION_DENIED` / `ESCALATION_NOT_DUE`, `BINDING_PAUSED`, `BINDING_REPLACED`, and malformed-input error behavior remains intact. Receipt `resulting_publication_revision` remains null for these controls.
5. **Time and bounded progression.** React samples authoritative database time once per evaluation unit (one case evaluation); `due_at <= sampled_at` counts as due, in UTC elapsed time. MDM independently checks `due_at <= statement_timestamp()` when accepting a request. React proposes at most one *next* level per case/evaluation, never skips a level, never replays missed polls, and imposes configured per-cycle admissions; a denied previously applied level must converge to no further automation for that occurrence until an operator acts or recurrence creates a new key. The maximum level is the active MDM binding limit.
6. **Safety and recovery.** The original due timestamp stays unchanged on escalation; time samples and audit/receipt updates do not salt request keys or make new action-driving revisions. Check binding, case, freshness, next-level and applied history under the existing transaction/lock order; do not admit stale/paused/replaced/unauthorized work. Previous applied receipts survive normal retries and coherent logical/physical restore under v3 retention, and restored bindings still require explicit activation. Dropping the whole entity is outside occurrence retention.

## Acceptance fixtures and open release inputs

- Positive: due boundary and distinct new occurrence; one level applied once, preserved due time; same-key replay returns the original receipt; two distinct request keys for a lowered case yield one application and then `ESCALATION_LEVEL_ALREADY_APPLIED` with no second control; evidence is independent of binding ID.
- Negative: non-next level returns `STALE_CASE` / `ESCALATION_NOT_NEXT`; paused binding `BINDING_PAUSED`; replaced binding `BINDING_REPLACED`; malformed level fails validation without a receipt; races, rollback, human changes, outage catch-up, restore, and clone activation have exact control/receipt-state comparisons.
- React issue #11 must still obtain missing owner-confirmed receipt fixtures and final evaluation/catch-up semantics, then implement managed time-only admission and diagnostics. React issue #12 must obtain signed numeric poll, backlog, retention/resource/recovery limits and full workload qualification. These are **not** silently approved by this engineering addendum.
- The receipt-history probe is deliberately schema-neutral. Its performance on retained histories requires measurement under the existing pg-trickle #1168 / React #12 throughput and storage gates; an index or schema migration is a separate reviewed change if warranted.
